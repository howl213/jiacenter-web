- 시험 실행은 지금 지침이 오히려 "내가 할 수 있는 확인은 직접 한다"(72줄)고 한다. 사용자가 확정한 기준(테스트는 별도 승인)과 반대 방향이다. 12-2-추가 A.

### 4-2. 확정된 정책 (3단 구조, 사용자 확정 2026-11-20)

| 단계 | 일 | 규칙 |
|---|---|---|
| **자유** | 파일 읽기와 구조 파악, 원인 조사·분석, 대안 비교, 개선점·추가 작업 **제안**, 요청한 작업의 범위와 위험요소 설명 | 시작 전에 매번 허락을 구하지 않는다. 막히면 묻기 전에 먼저 더 찾아본다 |
| **요청 범위 안** | 사용자가 **명시적으로 요청한** 파일 수정·생성, 그 작업을 끝내는 데 필요한 범위 내 작업 | 한다. 말뜻이 둘로 읽히면 한 줄로 묻는다. 아래 별도 승인 대상은 요청 범위 안이라도 예외다 |
| **별도 승인** | 요청 범위를 벗어난 기능 추가·개선 적용, 작업 범위 확대, **검사 명령 실행**(테스트, Django 검사, 마이그레이션 검사, 누출 검사, 트랙·Manifest 검사 등), 브랜치 생성·전환·삭제, 커밋·푸시·PR·병합, stash 생성·적용·삭제, Git 이력 변경, **`CLAUDE.md`·`.claude/settings.json`·`.claude/settings.local.json`·훅·권한·메모리 수정, `.claude/` 안 새 파일 생성(규칙·명령·스킬)** | 하지 않고 먼저 제안한다. 승인은 현재 작업에서 사용자가 구체적으로 허용한 작업 단위에만 적용된다(4-2-1) |

핵심: 조사·판단·개선안 제안은 자율적으로, 실행 권한은 승인받은 범위 안에서만. 테스트와 검사 명령은 작업에 필요해 보여도 **사용자의 명시적 승인 뒤에** 돌린다. 이 원칙은 훅 같은 자동 실행에도 똑같이 적용된다(4-2-3). 브랜치 생성·전환을 "작업 시작 때 자동 허용"하는 문구는 넣지 않는다.

### 4-2-1. 승인 단위와 테스트 승인 (사용자 확정 2026-11-20, A·F·G 처리 원칙)

**승인은 현재 작업에서 사용자가 구체적으로 허용한 작업 단위에만 적용한다.**

- 한 번의 승인을 세션 전체에 대한 포괄 승인으로 해석하지 않는다.
- 승인받은 작업과 다른 작업으로 범위가 바뀌면 다시 확인한다.
- 같은 작업의 필요한 재시도는 최초 승인 범위에 들어가는지 판단한다. 단 **명령이나 영향 범위가 달라지면 다시 승인**받는다.
- 검사 명령 실행, Git 상태 변경, 가드레일 파일 수정은 **서로 다른 승인 대상**이다. 하나를 승인받았다고 다른 것을 한 것으로 보지 않는다.
- 읽기, 코드 탐색, 정적 분석(명령을 실행하지 않는 분석) 등은 승인 없이 한다. **테스트 등 검사 명령 실행**은 필요해 보여도 사용자의 명시적 승인을 받은 뒤 한다. 실행 전에 **실행할 명령과 범위**를 알린다.
- `.claude/` 안에 새 규칙·명령·스킬 파일을 만드는 것도 별도 승인 대상이다. 이 보고서에 파일 생성 계획이 있다고 생성 권한이 생기지 않는다. 기존 파일 수정과 새 파일 생성 모두 승인받은 범위에서만 한다.
- 검사를 돌리지 않았으면 "미실행"과 이유를 쓴다. 미실행은 숨길 일이 아니고 문제도 아니다. 다만 미실행을 성공처럼 쓰지 않고, 검증하지 않은 것을 완료·정상이라고 단정하지 않는다(4-2-2).

**확정(2026-11-20)**: "정적 분석 등"의 경계는 이렇게 정해졌다. 정적 분석은 명령을 실행하지 않고 파일·코드·설정을 읽어 하는 분석이다. `manage.py check`, `makemigrations --check`, `check_leaks.sh`, `check_track.py`, `check_manifest.py`, `/verify` 안의 검사처럼 **프로젝트 상태를 확인하려고 명령을 실행하는 것은 모두 실행 전 승인 대상**이다(이전의 "경계 미정" 해소, 12-2 ① #14).

### 4-2-2. 작업 수행 완료와 검증 완료 (사용자 확정 2026-11-20)

두 개념을 분리한다.
- **작업 수행 완료**: 요청받은 수정·작성 작업을 마친 상태
- **검증 완료**: 실제 검사를 실행하고 결과를 확인한 상태

작업은 마쳤지만 검증을 실행하지 않았다면 "작업 완료, 검증 미실행"을 함께 보고할 수 있다. **검증까지 완료했다고 표현해서는 안 된다.**

핵심 요구: 실행할 수 있는 검증을 확인하지 않은 채 근거 없이 모든 작업이 끝났거나 정상이라고 단정하지 않는다. **미실행 자체는 문제가 아니다.** 이미 미실행이라고 정확히 보고하는 방식을 쓰고 있고, 그 방식을 유지한다. 새로 만들 정책은 미실행을 막는 것이 아니라 근거 없는 단정을 막는 것이다.

| 상황 | Claude 의 보고 |
|---|---|
| 검사를 실행하고 통과 | 실제 실행 명령과 확인한 결과를 근거로 통과 보고 |
| 검사를 실행하고 실패 | 실패 사실과 원인을 보고 |
| 검사를 실행하지 않음 | 미실행 사실과 이유를 명시 |
| 검사가 가능하지만 확인하지 않음 | 검증되지 않은 상태임을 명시하고 완료·정상 단정 금지 |
| 승인이 필요한 검사 | 실행할 명령과 범위를 제시하고 승인 요청 |
| 결과를 확인할 수 없음 | 성공으로 간주하지 않고 결과 불명으로 보고 |

### 4-2-3. 검사 실행 승인과 자동 실행 (사용자 확정 2026-11-20, 선정 가이드는 제안)

**확정된 것**
- **자유**: 파일 읽기·검색, 코드·설정 분석, 실행 흐름·의존성 파악, 정적 분석
- **실행 전 승인**: 테스트(`unittest`·`pytest`·`manage.py test`), Django 검사(`manage.py check`, 배포 관련은 `--deploy`), 마이그레이션 검사(`makemigrations --check`), 누출 검사(`check_leaks.sh`), Git 트랙·Manifest 검사(`check_track.py`·`check_manifest.py`), `/verify` 에 포함된 검사, 그 밖에 프로젝트 상태·검증 결과를 확인하려고 실제로 실행하는 명령
- **자동 실행에도 같은 원칙**: 훅이 자동으로 실행한다고 검사 실행이 허용되는 것은 아니다. 승인받지 않은 검사는 실행하지 않고, 실행하지 않았다면 미실행으로 기록한다. 미실행을 통과로 취급하지 않는다. 사용자가 승인한 명령과 범위를 넘어 실행하지 않는다.
- **Git 읽기 전용 조회**: 세션 시작과 응답 종료 때 `git status`, `git rev-parse`, `git rev-list`, `git config` 는 읽기 전용 목적으로만 자동 실행해도 된다. 자동 실행하지 않는 것: `git fetch`, 브랜치 생성·전환·삭제, `git add`·`commit`·`push`·`merge`, stash 변경, 이력 변경. Git 작업별 별도 승인은 그대로다.
- **Django 검사는 유지**: `manage.py check`, `makemigrations --check --dry-run`, `manage.py test`, 배포 관련 변경 시 `manage.py check --deploy` 는 필요한 경우 수행한다. 다만 훅이 승인 없이 자동 실행하지 않는다. **Claude 가 변경 내용과 위험도를 분석해 필요한 검사를 고르고, 실행 전에 명령과 범위를 알린 뒤 승인받아 실행한다.** Django 와 무관한 문서만 고친 작업에는 Django 검사를 무조건 요구하지 않는다.

**아직 확정하지 않은 것(제안, 사용자 결정 필요)**: 검사 선정 가이드. 아래는 Claude 가 후보를 고를 때 참고할 표이고, 실제 선택은 변경 내용에 따라 달라진다.

| 바뀐 것 | 후보 검사 (고른 뒤 명령·범위를 알리고 승인받는다) |
|---|---|
| README·`docs`·`99.result` 등 Django 와 무관한 문서만 | Django 검사를 요구하지 않는다. 문서에 개인정보·키가 들어갈 수 있으면 누출 검사를 제안할 수 있다 |
| `src/` 의 뷰·모델 로직 | `manage.py test`(관련 범위 또는 전체), 필요하면 `manage.py check` |
| 모델 변경 | `makemigrations --check --dry-run`, `manage.py test`, `manage.py check` |
| 설정·배포 관련(`settings.py`, `vercel.json`, `build.py`, `deploy/`, 환경변수) | `manage.py check --deploy`(운영 모드 환경변수 필요. CI 는 `DJANGO_DEBUG=0` 과 임시 키를 쓴다, 확인 `test.yml`), `manage.py test` |
| 템플릿·정적 파일 | `manage.py test`(화면 시험) |
| `harness_script/` 와 훅·시험에 묶인 `CLAUDE.md` 부분 | 하네스 시험(`unittest discover -s harness_script`) 또는 관련 시험 파일 |
| 커밋·PR 직전 | 누출 검사, 트랙·Manifest 검사를 상황에 맞게 제안 |
| 위에 해당하는 것이 없거나 승인이 없음 | 검사 없이 "작업 완료, 검증 미실행"을 이유와 함께 보고 |

**아직 정해지지 않은 자동 실행**: git `pre-commit`(`check_leaks.sh --staged`)과 GitHub Actions 는 Claude Code 훅이 아니라 git 이벤트·GitHub 서버에서 도는 것이다. 이번 확정이 이들에도 적용되는지는 사용자가 정하지 않았다(12-2 ② #28).

## 7. 권장 파일 구조

### 7-1. 구조

※ 이 구조는 **설계**다. 설계에 파일 생성 계획이 있어도 생성 권한이 생기지 않는다. `.claude/` 안 새 파일 생성(규칙·명령·스킬)은 각각 별도 승인 대상이다(4-2-1, 12-2-추가 G).

```text
CLAUDE.md                           상시. 추정 5,000~5,500자(현재 7,810자)
  ├ 목표 ①과 지금 단계, vuln 동결 한 줄
  ├ 작업 권한 (4-3 초안)
  ├ 사람이 정하는 것 (표 — 위치·제목 불변)
  ├ 작업 규칙 4줄 (원본 — 위치·글자 불변)
  ├ 절대 안 하는 것 (기계가 막는 것은 장치 이름만)
  └ 포인터 (README, 하네스 설명서, 규칙 파일)

.claude/rules/                      경로 한정 (Read/Write/Edit 로 맞는 파일을 만질 때 로딩, 확인)
  ├ src-code.md        paths: src/**           코드 방침
  ├ docs-update.md     paths: 99.result/docs/** 문서 갱신 표
  └ vuln-track.md      paths: docs/vuln-manifest.md, harness_script/export_for_team.py 등  ② 절차

.claude/commands/
  ├ verify.md          있음
  └ pr-flow.md         5절 작업 흐름·PR 본문 (사용자가 부를 때만)

.claude/settings.json               훅 4개 유지 + permissions.ask (가드레일 파일 편집) 후보
harness_script/                      훅 개선 후보: git add -A·restore·checkout -- . 묻기
99.result/docs/하네스-엔지니어링-설명서.md   4-1 상세, 75줄의 유지보수 정보
메모리                               고유 취향·사고 사례·결정만. 규칙 원문은 CLAUDE.md
```

### 7-2. 구성 요소별 역할과 한계

| 구성 요소 | 맡는 일 | 맡기지 않는 일 | 한계 (확인) |
|---|---|---|---|
| 루트 `CLAUDE.md` | 매 세션 알아야 할 목표·원칙·승인 정책 | 절차 상세, 장치 설명 | 문서: 강제 설정이 아니라 문맥. 200줄 이하 권장 |
| `.claude/rules/` | 파일 작업 때만 필요한 규칙 | **행동 규칙**(브랜치 전환, 대화 방식) | `Read`·`Write`·`Edit`·단일 파일 `cat` 등에서만 불러옴. `Glob`·`Grep` 은 문서에 없음(미확인) |
| 명령/스킬 | 사용자가 부르는 반복 절차 | 항상 지켜야 할 원칙 | 스킬은 설명만 시작 때 읽고 본문은 호출 때. 명령은 스킬과 합쳐졌고 파일 형식은 계속 지원 |
| 훅 | 행동 직전 확인, 결정적 검사 | 판단·말투·"질문엔 설명만" | 매처는 도구 이름 기준. 지금은 `Bash` 만 연결 |
| 권한 | 도구·경로 단위 allow/ask/deny | 명령 인자의 세밀한 제한 | 문서: Bash 인자 제한 패턴은 "fragile" |
| 메모리 | 사용자 취향·사고 사례 | 규칙 원문 | 시작 때는 색인만 |
| 하네스 설명서 | 장치의 상세·한계 | 상시 지침 | 읽을 때만 로딩 |

### 7-3. 파일을 나누는 것이 실제로 토큰을 줄이는가 (평가)

- **줄이는 곳**: 문서만 만지는 세션(이번 같은 세션)에서는 `src-code.md`·`vuln-track.md` 가 안 불러온다. 4-1·1절·5절 이동분이 확실한 절감이다.
- **안 줄이는 곳**: `src/` 를 건드리는 세션은 `src-code.md` 가 결국 불러온다. 절감이 없다. 불러온 규칙이 이후 계속 문맥에 남는지는 문서에서 확인하지 못했다(미확인).
- **누락 위험**: 경로 규칙은 파일을 **읽는 순간** 불러온다. `git switch vuln/…` 같은 **행동**은 어떤 파일도 읽기 전에 일어난다. 그래서 "vuln 은 시키기 전에 건드리지 않는다"는 상시 CLAUDE.md 에 **한 줄 남긴다.**
- **관리 비용**: 파일이 3개 늘면 낡는 곳도 3곳이 는다. 이 저장소는 문서가 낡아서 사고가 난 이력이 있다(메모리 `closing-report-scope`). 그래서 **규칙 파일은 3개를 넘기지 않는다.**

## 9. 예상 토큰 절감 효과와 위험

모든 수치는 **글자 수 기준 추정**이다. 실제 토큰은 재지 않았다. 한글의 글자당 토큰 비율은 확인하지 않았다.

| 항목 | 절감(추정) | 근거 | 위험 |
|---|---|---|---|
| CLAUDE.md 이동·축소 (4-1, 1절, 5절, 75줄, 중복) | 7,810 → **약 5,000~5,500자 (30~40%)** | 4-1 1,223자, 1절 605자, 5절 386자 중심(확인, 글자 수 세어 봄). 이전 진단의 40~55% 는 과대였다 | 경로 규칙이 안 불리면 누락(7-3) |
| 경로 규칙 (문서만 만지는 세션) | 세션마다 약 600~1,000자 더 줄 수 있다 | 로딩 조건이 파일 작업 시점(확인) | `src/` 작업 세션은 절감 없음 |
| 훅 대안 B (사용자 확정 방향) | 질문 1회당 50~120자. **추정이며 실제 토큰 절감으로 단정하지 않는다** | 5-2 | 낮음. 2번 줄 불변, 세 파일 함께 검토 |
| 훅 대안 D-2 (5번에 1번) | 질문 20번 기준 약 10,000자 | 678 × 20 × 0.8(계산) | 중간. 상태 저장과 시험 필요, 세션 구분 값 **미확인**. **보류**(검증 전까지 하지 않음) |
| 훅 대안 C | 질문 20번 기준 약 6,000~7,000자 | 계산 | 높음. 3·4번 줄의 안전망 확인 전에는 하지 않는다 |
| 지침 중복 | 취약 서버 금지 3곳→1곳, 단언 금지 4곳→2곳 | 6절 표 | 합치다 뜻이 바뀔 수 있다 |
| 자율성 | "자유" 단계가 문서에 생긴다 | 4절 | 문구가 "실행해도 된다"로 읽히지 않게 정해야 한다 |
| 승인 원칙 유지 | 3단 구조와 지침 파일 별도 취급으로 오히려 선명해진다 | 4절 | 권한 `ask` 로 승인 창이 늘어 느려질 수 있다 |

가장 큰 누락 위험 세 가지:
1. 경로 규칙으로 옮긴 행동 규칙이 안 불러지는 경우 → 행동 규칙은 상시에 남긴다.
2. 시험이 읽는 제목·글자가 바뀌어 시험이 깨지는 경우 → 7-4 의 계획대로 같은 PR 에서 맞춘다.
3. 규칙을 옮기며 "같은 말이 여러 곳"을 한 곳으로 합칠 때 **마지막 한 곳까지 지우는 경우** → 19번(취약 서버 금지)은 한 곳을 반드시 남기는 것을 완료 조건에 넣는다.

## 10. 공식 문서 참고자료

읽은 방법: web-fetch 하위 에이전트 4개가 아래 페이지를 읽어 인용과 요약을 돌려줬다. 인용문은 에이전트가 가져온 것이고, 각 답에 "요약 기반"이라고 밝힌 부분이 있어 아래에 따로 표시했다. 하네스가 일부 결과에 "지시문처럼 보이는 패턴(bypass-permissions 등)"이 있다고 표시했으나, 문서가 설명하는 설정 이름일 뿐이었고 어느 것도 따르지 않았다.

| 파일 권한 규칙 | `Read`·`Edit` 은 gitignore 문법. `Edit` 규칙은 파일을 고치는 **모든 기본 도구**에 적용. `Read` deny 는 같은 경로 Edit·Write 도 막는다. Bash 의 `cat`·`head`·`tail`·`sed`·`tee` 같은 인식된 명령과 리다이렉션에도 적용. `grep -r pattern .` 처럼 파일명을 안 쓰는 명령엔 안 된다 | 위와 같음 |
| Bash 권한의 한계 | "Bash permission patterns that try to constrain command arguments are fragile." `Bash(git push *)` 가 `git -C . push` 를 막지 않는다 | 위와 같음 |
| 설정 우선순위 | managed > 명령줄 > local > project > user. `deny`·`ask` 는 바로 적용, `allow` 는 폴더 신뢰 뒤 적용. 훅은 현재 폴더의 `.claude/` 만 읽고 상위 폴더로 올라가지 않는다 | https://code.claude.com/docs/en/settings |

### 문서에서 확인하지 못한 것 (미확인)

- `permissions` 안의 `ask` 배열 이름: 권한 문서 문장에는 "Ask rules" 가 있고 평가 순서에도 나오나, 설정 페이지의 JSON 예시는 `allow`·`deny` 만 보여 준다. 키 이름이 `ask` 인지는 **직접 JSON 예시로 확인하지 못했다.**

- `UserPromptSubmit` 의 `additionalContext` 가 매 메시지마다 누적되는지 교체되는지.
- Stop 의 `additionalContext`·`systemMessage` 가 설치된 버전에서 실제로 동작하는 방식(공식 문서상 지원은 사용자 제공 정보로 확인됨, 실동작은 미검증. 12-2 ④ D3 설계 ⑧-1a·⑨).

- 훅 입력에 세션을 구분하는 안정적인 값이 있는지(D-2 에 필요).
- 컨텍스트가 압축(compact)된 뒤 CLAUDE.md·훅 문구가 어떻게 되는지.
- 각 문서의 나머지 부분 중 에이전트가 요약만 한 구간.

#### 12-2 ④ #21 구현 설계안: 검증 완료 주장의 탐지 (D2 조사 반영, 제안)

이 소절은 위 표의 #21 행이 설계 과제로 남긴 "표현·증거 조합 판정"의 설계안이다. **#21~#25 의 확정 정책은 바꾸지 않는다.** 아래는 제안과 가설이며, 확정이 아니다. 판정 정확도는 검증하지 않았다(V13).

**조사 근거 (확인, 설계 가설의 근거일 뿐 탐지 정확도가 검증됐다는 뜻이 아니다)**
- 하네스 프로젝트 최종 응답 14개, 원본 프로젝트 최종 응답 472개(고유 416개, 56개는 여러 세션 기록에 중복).
- **집계 기준**: 전체 응답 472개 중 고유 응답은 416개다. 후보 응답 48건과 그에 따른 테스트 미실행 11건, 요약 줄 없음 14건, 마지막 실패 7건, 마지막 성공 16건은 고유 응답 기준이다. 비인용 통과 표본 24개와 HEDGE 가림 비율은 중복 제거 전 집계 기준이다.
- 원본 프로젝트의 비인용 "통과" 표본 24개 중 약 18개가 실제 결과 보고였다.
- 후보 응답 48건 중 테스트 미실행은 11건(23%)이었고, 이 11건에서는 `src/` 편집이 관측되지 않았다.
- `src/` 편집 후 테스트 없이 통과를 주장한 사례는 관측되지 않았다.
- 테스트 결과 요약 줄이 없는 사례는 29%였다.
- 전체 HEDGE 면제가 새 후보 문장이 있는 응답의 약 65% 를 가렸다(중복 포함 기준, 분모·분자는 이 보고서에서 다시 확인하지 않았다). 같은 면제가 기존 `CLAIM` 의 오탐(규칙 인용·권고 문장)을 일부 걸러 주기도 했다.

**① 초기 탐지 표현 (제안)**
1. 숫자 + `개`/`건` + `통과`
2. 시험·테스트·검사·점검 문맥의 통과 표현(`통과했다` 류)
3. `모두 통과`

**② 초기 제외 표현 (제안)**
- 작업·수정·반영 완료(작업 완료는 허용, 4-2-2).
- `정상`, `성공`, `안전`, `확인했습니다` 단독.
- `검증 완료`, `정상 동작`, `이상 없음` 은 실제 사례가 부족해 **후순위**로 보류한다.

**③ 문맥 판별 (제안)**: 아래는 검증 완료 주장으로 보지 않는다 — 코드 블록·백틱 안, 일반 인용, 권고, 사용자 결과 중계, 예측·추정, 부정·조건·질문·예정, 훅의 pass-through 로 쓰인 "통과". 표 전체를 무조건 제거하지 않는다. **CI·테스트 결과 표와 설명 표를 구분하는 방식은 미결정이다.**

**④ HEDGE (제안)**: 새 탐지 층에는 전체 응답 HEDGE 면제를 적용하지 않고, 부정·조건·질문·미실행 판정을 문장 단위로 한다. **기존 `CLAIM` 층의 HEDGE 처리는 영향과 오탐을 따로 검토한 뒤 정한다(미결정).**

**⑤ 탐지와 증거의 결합 (제안)**: 탐지만으로 차단하지 않는다. 이번 턴의 편집 여부·경로, 이번 턴에 실행된 테스트, 테스트의 종류와 범위, 출력에서 확인되는 성공·실패 증거를 결합한다.

| 증거 상태 | 설계 방향 (구현 설계안, 정책 아님) |
|---|---|
| 증거 없음 | 이번 턴 관련 편집이 있고 검증 완료를 주장하는데 실행 증거가 없으면 근거 부족으로 판단할 수 있다. **구체적인 차단 조건은 D3 에서 확정할 부분으로 남긴다** **[D3-1 로 확정: 관련 편집 + 통과 주장 + 증거 없음 → 1회 차단. 원문은 보존한다]** |

명확한 실패 기록이 있는데 성공이라고 쓴 경우는 위 세 상태와 별도로 다룬다(아래 B·J 상태 구분표의 "실패 기록 + 완료·통과 단정").

**⑥ D3 에서 정할 것 (여기서 확정하지 않는다)**: 하네스·프로젝트 테스트를 가르는 분류 방식(#23), 출력 본문에서 성공·실패를 판정하는 방법(요약 줄 형식, 파이프·`|| true`), 마지막 시험 결과만 볼지 이번 턴 순서 전체를 볼지(성공 뒤 실패로 끝난 턴이 5건 있었다), 요약 줄이 없는 29% 의 원인, "증거 없음"의 구체적인 차단 조건. **[D3 검토(2026-11-20)에서 정리됨: 결정은 아래 "#21 D3 설계" 소절 ⑧, 남은 것은 ⑨. 이 문단은 D2 시점의 원문 그대로 보존한다]**

**⑦ 한계**: 표본은 한 작성자의 특정 기간 기록이다. 사례 분류는 균등 간격 표본을 직접 읽은 수동 분류이고 비율에 오차가 있다. 조사 과정에서 계산한 키워드 빈도는 중복 응답을 제거하지 않은 기준이며, 해당 빈도표는 본 보고서에 수록하지 않았다. `src/` 편집이 드물어 증거 결합의 실제 효과는 검증하지 못했다. 정확도(오탐·미탐)는 이후 시험으로 확인해야 한다.

**⑧-1a Stop 출력 필드의 확인 상태 (최종 감사 M1 반영)**

아래 내용은 사용자가 공식 Claude Code Hooks 문서(https://code.claude.com/docs/en/hooks) 기준으로 확인해 제공한 것이다. **이 보고서를 쓴 쪽은 문서 원문을 직접 열지 않았다(네트워크 미사용).** 앞서 "지원 여부 미확인"으로 적힌 이유는 10절의 Stop 행이 "요약 기반"이고 출력 필드를 다루지 않았기 때문이다.
- Stop 이벤트는 `hookSpecificOutput.additionalContext` 를 지원한다. `hookSpecificOutput` 안에 `hookEventName: "Stop"` 을 지정한다.
- `additionalContext` 는 Claude 의 다음 모델 요청에 전달되는 문맥이다. Stop 이벤트에서는 턴 종료 시점에 전달되고, 대화는 피드백에 대응할 수 있도록 이어진다.
- `systemMessage` 는 사용자에게 보여 주는 메시지다. 두 필드를 혼동하지 않는다.

출력 구조 예시(설계 예시이며 문구는 확정이 아니다):

```json
{
  "hookSpecificOutput": {
    "hookEventName": "Stop",
    "additionalContext": "검증 결과가 불명확합니다. 성공으로 단정하지 말고 결과를 확인하세요."
  }
}
```

**[구현 변경 2026-11-20, ⑪]** 위 예시는 설계 당시 것이다. 구현은 재검사 출력에 `additionalContext` 를 쓰지 않고 `systemMessage` 만 낸다.

| 구분 | 상태 |
|---|---|
| 공식 문서상 지원 | 확인됨 (사용자 제공, 출처 위 URL) |
| 설치된 Claude Code 버전에서의 실제 동작 | 미검증 |
| 프로젝트 통합 테스트 | 미실시, 구현 후 검증 |

**⑧-1b 증거 상태 정의와 판정표 (최종 감사 M3 반영, 사용자 지시)**

범위(`src/` 또는 하네스, D3-4)마다 따로 판정한다. 아래 정의에서 "해당 범위"는 그 판정 대상 범위를 뜻한다.
- **증거 없음**: 해당 범위에서 관련 검증 실행 기록이 없다. 다른 범위의 실행 기록만 있는 경우도 해당 범위에서는 증거 없음이다.
- **증거 불명**: 관련 검증 명령은 실행됐지만 출력·종료 결과가 불완전하거나 성공 여부를 확정할 수 없다.
- **성공**: 해당 검증 유형에 정의된 성공 조건을 충족하고 실패 표지가 없다.
- **실패**: 해당 검증 유형에서 실패가 명확히 확인된다.
- **성공 주장**: D2 ① 의 탐지 3패턴에 걸리고 D2 ③ 의 문맥 제외에 걸리지 않은 문장.

| 관련 편집 | 해당 범위 검증 | 결과 | 성공 주장 | 처리 |
|---|---|---|---|---|
| 있음 | 없음 | 증거 없음 | 없음 | 차단하지 않음 |
| 있음 | 없음 | 증거 없음 | 있음 | 1회 차단 |
| 있음 | 있음 | 성공 | 있음 | 통과 |
| 있음 | 있음 | 실패 | 있음 | 성공 단정 차단 |
| 있음 | 있음 | 불명 | 있음 | 1회 차단 |
| 있음 | 있음 | 불명 | 없음 | 경고 또는 미검증 표시 |
| 없음 | 없음 | 증거 없음 | 있음 | 초기 버전에서는 미탐 허용 (D3-3) |
| 없음 | 있음 | 성공 | 있음 | 결과 보고로 허용 |
| 없음 | 있음 | 실패 | 있음 | 해당 검증 결과의 성공 단정은 허용하지 않음 |
| 없음 | 있음 | 불명 | 있음 | 결과 불명으로 안내 |

실패 기록과 통과 주장의 처리:
- 실패가 확인된 동일 검증 범위의 전체 성공 주장은 허용하지 않는다.
- 일부 성공과 일부 실패를 함께 설명하는 경우 D3-5 의 같은 문장 내 실패·통과 예외 조건을 적용한다.
- 답변 어딘가에 "실패"라는 단어가 있다는 이유만으로 통과 주장을 면제하지 않는다.
- "3개 실패. 47개 통과." 처럼 문장이 나뉜 경우는 자동으로 면제하지 않는다. 부분 결과를 정확하게 보고할 수 있는 표현인지는 구현 테스트에서 별도로 검토한다(**[미확정]**). 이 판정표와 D3-5 가 B·J 상태표의 "실패 기록 + 실패 보고" 행보다 우선한다.

- **테스트**: `Ran M`(M≥1), `OK`, 실패 표지 없음 등 ⑧-2 의 기준을 적용한다.

- **Django 검사**(`manage.py check`·`makemigrations --check`): 테스트 결과와 별도 기준이 필요하다. **[미확정]**

**⑧-2 유지하는 설계 (검토에서 채택)**
- **[유지]** `src/` 와 하네스 범위를 각각 독립적으로 판정한다. 각 범위에서 **마지막 관련 편집 이후 실행된 마지막 관련 검증**을 기준으로 삼는다. 다른 범위의 테스트는 해당 범위의 증거가 아니다. 문서 등 무관한 경로의 편집은 기존 증거를 무효화하지 않는다.
- **[유지]** 성공은 **양의 증거로만** 인정한다. 초기 성공 판정 후보: `is_error=false` + `Ran M` 에서 M≥1 + `OK` 존재 + 실패 표지(`FAILED`·`Traceback`·`Exit code` 0 아님 등) 부재를 모두 만족. 실패 표지가 성공 표지보다 우선한다. 요약이 여러 개면 모두 성공이어야 한다.
- **[유지]** 파이프·`|| true`·`;`·명령 연결 등 결과를 신뢰하기 어려운 형태는 보수적으로 **증거 불명**으로 처리한다. 판정 대상은 오탐(성공 오인) 쪽이 아니라 불명 쪽으로 틀리게 둔다. (`claude_guard.py` 의 `segments()` 는 연산자 종류를 돌려주지 않고 파이프 여부만 준다 — 코드 확인. 원문 문자열 검사로 보완하는 방식은 구현 설계 과제다.)
- **[유지]** 최종 답변 판정은 `last_assistant_message`(없으면 transcript 의 마지막 글), 도구 실행·편집 기록은 transcript 로 본다. `Bash` 로 직접 한 파일 수정은 현재 추적 한계로 남긴다(`Edit`·`Write`·`NotebookEdit` 만 센다, `stop_check.py` 117~122줄).
- **[유지]** 이번 단계에서 `claude_guard.py`·`verify.sh`·`.claude/settings.json` 은 실제 구현을 수정하지 않는다(코드 확인: `claude_guard.py` 의 헬퍼를 고치지 않고도 구현 가능한 구조다).
- **[미확정, 검토 의견]** `verify.sh` 는 성공한 단계의 하위 출력을 버리고 `통과  <단계명>` 한 줄만 찍는다(`verify.sh` 11줄, 코드 확인). 그래서 "`Ran N`+`OK`" 규칙만으로는 항상 불명이 된다. **`통과` 문구만으로 성공을 인정하지 않는다.** 단계별 실제 종료 결과와 연결하는 별도 증거 규칙이 필요하다(⑨). 설계 방식은 정해지지 않았다.

**⑩ 구현 계획 (제안, 구현 안 함)**: (1) D3 결정 확정(D3-1~D3-6, 판정표 ⑧-1b 포함) → (2) 명령 분류·출력 판정·통과 주장 탐지 순수 함수 설계 → (3) `check()` 연결 및 관련 단위 테스트 개편 → (4) Stop 훅 재검사 및 안내 출력 구현 → (5) 기존 세션 기록 오프라인 재생으로 오탐·미탐 조사 → (6) Django 자동 검사 제거(2차-가, 7-4 의 용어 정의)는 별도 단계로 분리. **테스트 실행과 기록 재생은 실행 전에 사용자 승인을 받는다.** 하네스 테스트 통과는 하네스 훅 동작의 확인일 뿐 프로젝트 코드 검증이 아니다(#23).

**⑪ 구현 변경과 검증 상태 (2026-11-20, 4단계 실제 이벤트 검증 뒤)** — 아래는 현재 구현이며 위 D3-6·⑧-1a 의 `additionalContext` 서술보다 우선한다. D3 결정 번호와 판정표는 바뀌지 않는다.
- **A. Stop 피드백과 도구 기록**: 실제 transcript(Claude Code 2.1.329)에서 Stop 훅이 막은 뒤 들어오는 피드백은 `type: user`, `isMeta: true`, 내용이 `Stop hook feedback:\n` 으로 시작하는 항목이었다. 세 조건을 모두 만족하는 항목만 Stop 피드백으로 보고, `turn_tool_uses` 는 이 항목에서 이전 도구 기록을 지우지 않는다. 일반 사용자 메시지는 기존처럼 기록을 지운다. (이전에는 피드백이 일반 사용자 입력처럼 취급되어 재검사 때 편집 기록이 사라졌다.)
- **B. 최초 Stop (`stop_hook_active=false`)**: 검사하고, 차단 조건이 있으면 `decision: block` 과 `reason`, 없으면 통과.
- **C. 재검사 Stop (`stop_hook_active=true`)**: 검사를 다시 한다. 해결됐으면 통과, 문제가 남았거나 새 문제가 나오면 `systemMessage` 만 낸다. `decision`·`reason`·`additionalContext` 는 내지 않고, 모델에게 일을 시키지 않는다. 사용자에게 상황을 알리는 용도다. 이유: 실제 이벤트에서 `additionalContext` 출력이 모델을 다시 불러 Stop 훅이 총 9번(최초 1 + 재검사 8) 호출됐다.
- **E. 후속 구현(2026-11-20)**: ① **2차-가 완료** — 훅이 `manage.py check`·`makemigrations --check` 를 직접 실행하던 블록을 없앴다(결정 #6 ③⑤, #19). `git status` 조회는 읽기 전용으로 유지한다(#22). `DjangoCheck` 시험은 "실행하지 않는다"를 확인하는 `NoDirectDjangoRun` 으로 교체했다. ② **안내(notices) 출력 연결** — 막을 것은 없고 결과 불명 안내만 있으면 막지 않고 `systemMessage` 만 낸다. 최초 차단이 있으면 같은 `reason` 에 "참고"로 붙이고, 재검사에서는 `systemMessage` 하나에 합친다. 주장이 있는 불명은 여전히 차단 사유다. 현재 단위 테스트 121개 통과, 통합 검증은 미완료.
- **D. 유지**: 입력 JSON 파싱 실패는 fail-closed, 기존 판정 정책, 편집 범위 추적. Auto 모드를 기본 운영 방식으로 쓴다 — 불필요한 수동 승인을 늘리지 않되, Auto 모드에서도 하네스의 통제 경계(위험 명령 훅, 승인이 필요한 푸시·PR·병합·브랜치 작업)는 그대로다.

3. 훅의 침묵을 "검증 성공"으로 읽지 않는다. 훅이 아무 말도 하지 않는 것은 "차단할 근거가 없다"는 뜻일 뿐이다.

#### D 안(案): 표준 작업 흐름을 "고르는 절차"로

| 6 | "시안·초안만 커밋 전에 묻는다"는 시안이 아닌 것은 묻지 않고 커밋해도 되는 것처럼 읽힌다 | 확정 원칙과 반대로 읽힐 수 있다 |

수정 방향(적용 안 함): 별도 승인 대상의 **목록은 새 "작업 권한" 절(4-3)이 가진다.** 4번 줄은 그 절을 가리키는 짧은 문장이 되고, 그 안에 (a) 커밋·푸시·PR·병합·브랜치 생성·전환·삭제·stash·이력 변경·시험 실행·지침 파일 수정·`.claude/` 새 파일 생성은 모두 사용자가 **그 일을** 승인한 뒤에만 한다, (b) 시안은 커밋 전에 먼저 보여 준다, (c) 하네스·지침 변경 보고는 "켜짐/안 켜짐"부터 쓴다를 담는다. 2번 줄은 그대로 둔다.

시험 연동(확인): `test_prompt_reminder.py` 의 4번 줄 핵심 말은 `끝났을 때만`, `커밋할까요`, `푸시`, `PR`, `병합`, `승인`, `켜짐/안 켜짐` 이다. "끝났을 때만 커밋"을 고치면 이 목록과 훅 4번 줄·`CLAUDE.md` 4번 줄이 함께 바뀌어야 한다. 위 1번 어긋남을 고치려면 불가피하다.

### 12-3. 미확인

- 10절 말미의 문서 미확인 7가지
- `claude_guard.py` 가 실제 세션에서 도는 모든 경우(설명서 8절도 "나중에 추가한 묻기는 시험으로만 확인"이라고 적음)
- 추정 출결 시각 자동 입력 금지와 `_toggle` 단일 입구를 직접 지키는 시험이 있는지
- `audit.yml` 의 실제 실행 기록(설명서에 "없음"으로 적혀 있음)
- 세션을 `src/` 에서 열었을 때 훅이 로딩되는지
- 개별 메모리·규칙 파일이 압축(compact) 뒤에 어떻게 되는지
- 토큰 실측치(이 문서의 모든 절감량은 글자 수 기반 추정)
- 사용자가 사용하는 권한 모드(관찰로는 편집 승인 창이 떴다는 것까지만 안다)
- 자동 실행 정책 재설계의 기술 미확인 사항은 12-2 ③ V9~V16 에 모았다(`git fetch` 의 `.git` 변화, 로그 파일·DB 부작용의 실제 실행 검증, 세션 기록의 승인·거절 형식, Stop 훅 출력 채널의 설치 버전 실동작(공식 문서상 지원은 사용자 제공 정보로 확인됨, ⑧-1a), 단정 판정의 정확도 등)

이 문서의 결과는 설계안이다. 사용자가 읽고 단계를 승인하기 전에는 어떤 개편도 시작하지 않는다.
