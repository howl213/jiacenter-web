## 갱신 지침

### 언제 갱신하나

**아직 안 끝난 것이 생기거나 끝났을 때만.** 이 문서는 외부 확인 대기·사용자 결정 대기를 짧은 표 한 줄씩 적는 곳이다.
"무엇을 했고 어떻게 확인했다"는 작업 기록은 커밋과 PR 본문에 둔다(줄글이 쌓이면 낡은 문서가 된다). `CLAUDE.md` 1절과 같은 규칙이다.

| 상황 | 할 일 |
|---|---|
| 외부 확인이나 사용자 결정을 기다리는 것이 생겼다 | C(외부)·E(결정) 칸에 표 한 줄 **추가**. 새 항목은 채팅에 먼저 말하고 승인받은 뒤 적는다 |
| 기다리던 것이 끝났다 | ☐ → ☑ 로 바꾸거나 지운다. 결과는 커밋·PR 본문에 |
| 외부 답변을 받았다 | 해당 `외부문의/` 문서와 표를 함께 갱신 |
| 결정이 내려졌다 | E 에서 지우고, 결정 내용을 README 나 코드 주석에 남긴다 |
| 새 위험을 발견했다 | "알려진 미해결 위험" 에 추가하고 `SECURITY_REVIEW.md` 에도 반영 |

### 어떻게 적나

**"확인했다"가 아니라 "무엇을 어떻게 확인했는지"를 적는다.**

나쁜 예:

```
☑ CSV 정상 동작 확인
```

좋은 예:

```
☑ CSV 수식 인젝션 차단 — `=1+1` → `'=1+1`, `@SUM(A1)` → `'@SUM(A1)`,
  `병원 진료` → 그대로. BOM 있음. (2026-11-05)
```

이유: 나중에 읽는 사람이 **그 확인이 무엇을 보장하고 무엇을 보장하지 않는지** 판단할 수 있어야 한다.
"정상 동작 확인"은 아무것도 보장하지 않는다.

### 적지 않는 것

- 코드를 보면 알 수 있는 것 (구조, 함수 이름) → 코드 주석이나 README 로
- 이번 작업에서만 의미 있는 임시 메모 → PR 본문으로
- 외부 기관 답변을 추측해서 채우는 것 → **금지.** 모르면 ☐ 로 둔다

### 주장에는 근거를 붙인다

수치·버전·외부 정책은 **실제로 확인한 것만** 적는다. 기억에 의존해 적지 않는다.

| 쓰는 법 | 예 |
|---|---|
| 명령 결과 | `pip-audit` → `No known vulnerabilities found` |
| API 응답 | `403: Upgrade to GitHub Pro or make this repository public` |
| 공식 문서 | 링크를 함께 |
| 확인 못 함 | "미확인" 이라고 명시 |

### PR 과의 관계

PR 템플릿에 **"확인하지 않은 것"** 칸이 있다. 거기 적은 내용 중 **다음 작업까지 남는 것**을
`확인사항.md` 로 옮긴다. PR 본문은 묻히고, 이 문서는 계속 읽힌다.
