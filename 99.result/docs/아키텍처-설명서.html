1. 한 줄로 이해하기 (식당 비유)

손님(브라우저)이 식당(우리 사이트)에 주문하는 장면으로 보면 쉽다.

식당우리 사이트하는 일
문 앞 안내원 겸 경비Caddy바깥(인터넷)과 처음 만나는 곳. 암호화(HTTPS)를 맡고, 들어온 손님의 주문을 안으로 넘긴다.
주문 전달 직원 (2명)gunicorn (workers 2)안내원이 넘긴 주문을 Django 가 읽을 수 있는 형식으로 바꿔 전달하고, 결과를 다시 받아 돌려준다.
주방장Django"이 사람이 이 화면 봐도 되나?"를 확인하고, 창고에서 재료를 꺼내 화면(HTML)을 만든다.
창고db.sqlite3 · media/아이 명단·출결·공지·사진이 보관되는 곳.
식당 관리자(사장님 대신 문 열고 닫음)systemd서버가 켜질 때 gunicorn 을 자동으로 켜 주고, 죽으면 다시 켜 준다.

핵심: 손님은 Caddy 한 곳만 만난다. gunicorn 과 Django 는 서버 안쪽(127.0.0.1)에만 열려 있어서 바깥에서 직접 두드릴 수 없다.

2. "이 모델들"의 정체 — 낯선 이름 사전

용어 정리 말씀하신 "모델"은 정확히는 "서버에서 같이 돌아가는 프로그램(소프트웨어 부품)"이다. 헷갈리기 쉬운 점: 이 저장소에서 "모델"이라는 말은 center/models.py 의 DB 표(아동·공지·출결 등 10개)를 뜻하기도 한다. 그건 완전히 다른 얘기다.
이름정체없으면?
Caddy웹 서버 / 리버스 프록시(손님 대신 안쪽 서버에 말 걸어 주는 문지기). 특기는 HTTPS 인증서를 자동으로 받아서 갱신해 주는 것.HTTPS 를 직접 해결해야 한다. 또 Django 가 바깥에 직접 노출된다.
gunicornWSGI 앱 서버. 파이썬 웹 프로그램(Django)을 "실제 운영용으로" 돌려 주는 프로그램. 여러 요청을 동시에 처리하려고 프로세스를 여러 개(--workers 2) 띄운다.manage.py runserver 로 대신 돌려야 하는데, 그건 개발용이라 운영에 쓰면 안 된다.
WSGI"웹 서버 ↔ 파이썬 프로그램" 사이의 약속(규격). 이 약속 덕분에 gunicorn 과 Django 가 서로 몰라도 붙는다. 이 저장소의 접점은 config/wsgi.py 의 application.(규격이라 따로 설치하지 않음)
systemd리눅스에 원래 있는 프로그램 관리자. "서버 켜지면 gunicorn 실행, 죽으면 재시작"을 맡는다. 설정은 deploy/jiacenter.service.gunicorn 을 터미널에서 손으로 켜야 하고, 창을 닫거나 서버가 재부팅되면 사이트가 꺼진다.
WhiteNoiseDjango 안에 끼워 넣는 작은 부품. CSS·글꼴·이미지 같은 정적 파일을 Django 가 직접 내주게 한다. 운영(DEBUG=0)에서만 켜진다.운영에서는 Django 가 정적 파일을 안 내줘서 화면 스타일이 다 깨진다. (개발용 runserver 는 알아서 내줌)
Django파이썬 웹 프레임워크. 이 사이트의 본체. 주소 → 함수(views) → DB(models) → 화면(templates).사이트 자체가 없음.
SQLite (db.sqlite3)파일 하나짜리 데이터베이스. 별도 DB 서버 프로그램이 필요 없다.—
.env비밀번호·키 같은 설정을 코드 밖에 두는 파일. 커밋하지 않는다(.gitignore).비밀키가 코드에 들어가 저장소에 새어 나간다.
collectstaticDjango 명령. 흩어진 정적 파일을 staticfiles/ 한 폴더에 모은다. WhiteNoise 는 그 폴더를 내준다.운영에서 CSS 를 못 찾는다.

4. 부품별 자세히

4-1. Caddy — deploy/Caddyfile

example.kr {
	reverse_proxy 127.0.0.1:8000
}

이 세 줄이 전부다. 해석:

  • example.kr { … } — "이 도메인으로 오는 요청을 내가 받는다." 도메인을 이렇게 적으면 Caddy 가 HTTPS 인증서를 스스로 받아 오고 갱신한다(Caddy 의 기본 동작 — 공식 설명 기준이고, 이 저장소에서 직접 돌려 확인하지는 않았다).
  • reverse_proxy 127.0.0.1:8000 — "받은 요청을 같은 서버 안의 8000번 포트(= gunicorn)에 넘겨라."
  • Caddy 가 X-Forwarded-Proto 헤더를 스스로 채워 보낸다고 파일 주석에 적혀 있다. 이게 아래 4-4 의 열쇠다.
  • 인증서를 받으려면 보통 도메인이 이 서버 IP 를 가리켜야 하고, 80·443 포트가 열려 있어야 한다(일반적인 조건. 실제 환경에서는 미확인).

4-2. gunicorn — deploy/jiacenter.service 의 ExecStart

/srv/jiacenter/.venv/bin/gunicorn config.wsgi -b 127.0.0.1:8000 --workers 2
  • config.wsgi — "파이썬 파일 config/wsgi.py 안의 application 을 실행해라." (Django 로 들어가는 문)
  • -b 127.0.0.1:8000 — 내 컴퓨터 안쪽에서만 8000번으로 받는다. 0.0.0.0 이 아니라서 인터넷에서 직접 못 들어온다. Caddy 를 거쳐야만 닿는다.
  • --workers 2 — 일꾼(프로세스) 2개. 요청 2개를 동시에 처리할 수 있다. 일꾼은 서로 메모리를 공유하지 않는다.

4-3. systemd — deploy/jiacenter.service

줄뜻
After=network.target네트워크가 준비된 뒤에 시작
User=jiacenter관리자(root)가 아니라 권한이 작은 전용 계정으로 실행. 뚫려도 피해 범위를 줄이려는 것.
WorkingDirectory=/srv/jiacenter코드를 둘 폴더(견본 경로)
EnvironmentFile=/srv/jiacenter/.env이 파일의 값들을 환경변수로 주입. 비밀키는 여기에만 있다.
Restart=on-failure비정상 종료하면 자동 재시작
WantedBy=multi-user.target서버 부팅 시 자동 시작 대상에 포함 (systemctl enable 했을 때)

4-4. Django 와 "프록시 뒤" 설정 — config/settings.py

Caddy 가 HTTPS 를 풀고 gunicorn 에는 평범한 HTTP 로 넘기기 때문에, Django 눈에는 모든 요청이 http 로 온 것처럼 보인다. 그런데 운영 설정은 이렇다.

if not DEBUG:
    SECURE_SSL_REDIRECT = True      # http 로 오면 https 로 돌려보냄
    SESSION_COOKIE_SECURE = True    # 세션 쿠키는 https 로만
    CSRF_COOKIE_SECURE = True
    SECURE_HSTS_SECONDS = 3600      # 브라우저에 "앞으로 https 로만" 기억시킴
    ...
    if os.environ.get('DJANGO_BEHIND_PROXY') == '1':
        SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')

그래서 Caddy 의 "원래 https 였어요" 쪽지(X-Forwarded-Proto)를 Django 가 믿어야 한다. 그 스위치가 DJANGO_BEHIND_PROXY=1.

두 방향으로 틀리면 생기는 일 (코드를 읽고 추론한 것, 실제 서버에서 재현은 안 함)
  • 스위치를 안 켬: Django 는 계속 "http 로 왔네" → 계속 https 로 돌려보냄 → 무한 리다이렉트 가능성.
  • 프록시가 없는데 켬: 누구나 X-Forwarded-Proto: https 헤더를 위조해 보낼 수 있어 https 검사를 속인다. .env.example 에 "프록시 없이 1 로 두면 안 된다"고 적힌 이유.

4-5. 미들웨어 — Django 입구의 검문 줄

요청이 views 에 닿기 전에 위에서 아래로 차례로 지난다(응답은 아래에서 위로).

순서이름하는 일
1Securityhttps 강제·HSTS 같은 보안 헤더

코드는 같고, 환경변수 DJANGO_DEBUG 하나로 모드가 갈린다(기본값 1 = 개발).

실행python manage.py runserversystemd → gunicorn(워커 2)

6. 파일과 데이터는 어디에 저장되나

무엇어디메모
DBBASE_DIR/db.sqlite3아동·출결 등. 커밋 금지. 지금은 모의 값만.
업로드BASE_DIR/media/공지 첨부·앨범 사진. 커밋 금지.
모아 둔 정적 파일BASE_DIR/staticfiles/collectstatic 결과. 커밋 안 함(생성물).
일반 에러 로그logs/error.log5MB 씩 4개(현재 + 백업 3)를 돌려 씀. 에러 추적에 요청 내용이 섞일 수 있어 DB 와 같은 수준으로 관리.
보안 로그logs/security.log로그인 실패·잠금, 키오스크 잠금, 명단 가져오기. 요청 내용은 안 남긴다.
비밀 설정서버의 .env권한 600, 커밋 금지.

알림톡(notify.py)은 아직 외부 API 에 연결되지 않았다. 발송 기록(NotifyLog)만 남긴다.

8. 처음 서버에 올릴 때 순서 (견본 기준 — 아직 실행해 본 적 없음)

저장소에 순서를 적은 문서는 없고, 아래는 deploy/ 파일과 settings.py 주석을 이어 붙인 예상 순서다. 실제로 하면 달라질 수 있다.

  1. 서버에 코드를 두고(/srv/jiacenter), 가상환경을 만들어 pip install -r requirements.txt
  2. .env 를 만든다 (.env.example 복사 → 값 채우기, 권한 600)
  3. python manage.py collectstatic — 정적 파일 모으기
  4. python manage.py migrate — DB 표 만들기
  5. deploy/jiacenter.service → /etc/systemd/system/ 로 복사, 경로·계정 수정 → systemctl enable --now jiacenter
  6. Caddy 설치 → deploy/Caddyfile 의 example.kr 을 실제 도메인으로 바꾸고 적용
  7. systemctl status jiacenter 와 logs/error.log 로 확인 (service 파일 주석이 이렇게 하라고 적어 둠)

실제 정보로 전환하기 전 점검표는 99.result/docs/확인사항.md 의 "실제 데이터 투입 전 체크리스트"를 본다.

9. 자주 나올 질문

Q. Caddy 와 gunicorn 은 둘 다 "웹 서버"인데 왜 둘이 필요해?

역할이 다르다. Caddy 는 바깥 인터넷 전문(HTTPS, 이상한 요청 걸러내기), gunicorn 은 파이썬 프로그램 실행 전문이다. gunicorn 만 바깥에 열면 HTTPS 를 직접 처리해야 하고, 느리게 오는 요청이나 이상한 요청에도 그대로 노출된다. 역할을 나누는 건 흔한 구성이다.

Q. 워커가 2개면 사용자 2명까지만 접속 가능해?

아니다. "동시에 처리 중인 요청"이 2개까지라는 뜻이고, 나머지는 줄을 서서 기다린다. 요청 하나는 보통 아주 짧게 끝난다. 이 규모(센터 하나)에서 2 가 충분한지는 부하를 걸어 본 적이 없어 미확인이다.

Q. SQLite 로 운영해도 돼?

파일 하나 DB 라서 간단하지만, 여러 워커가 동시에 쓰기를 하면 서로 기다리는 구간이 생길 수 있다. 센터 규모에선 흔히 문제 없다고 알려져 있지만, 이 사이트에서 실제로 확인한 것은 아니다. 또 서버 디스크가 날아가면 DB 도 같이 날아가므로 백업 방법은 따로 정해야 한다(지금 저장소에는 없음).

Q. CI(GitHub Actions)는 서버 배포랑 관계있어?

지금은 배포를 하지 않는다. PR 마다 테스트·bandit(보안 정적 검사)·마이그레이션 누락·개인정보 검사·check --deploy(운영 설정 점검)를 돌려서 "올려도 되는 코드인지" 검사만 한다. audit.yml 은 매주 월요일 의존성 취약점을 점검한다. 서버에 자동으로 올리는 단계는 없다.

Q. "바이브 코딩"으로 만든 구조인데 어디부터 이해하면 돼?

추천 순서: ① 3절 요청의 길 → ② config/settings.py 의 if not DEBUG: 블록(운영 모드가 뭘 바꾸는지) → ③ deploy/ 두 파일(합쳐서 30줄 남짓) → ④ center/urls.py 와 views.py 한 개(예: notice_list).

10. 아직 모르는 것 · 한계

  • 실제 서버에서 Caddy·systemd·gunicorn 을 조합해 돌려 본 적 없다. (architecture.svg 도 "이 PC 에서 gunicorn 만 띄워 확인"이라고 적음.) 확인하려면 클라우드에 올려 보는 단계(지금 계획의 마지막)를 거쳐야 한다.
  • example.kr 은 자리표시자. 실제 도메인·DNS·방화벽(80/443) 설정은 정해지지 않았다.
  • HSTS 는 3600초(1시간)로 짧게 켜 놓았다. 서버가 안정되면 늘릴지는 사용자 결정 사항이다.
  • 백업·모니터링(서버가 죽었을 때 알림)은 저장소에 없다.
  • 프록시 뒤에서는 Django 가 보는 접속자 주소(REMOTE_ADDR)가 전부 Caddy 의 127.0.0.1 로 보일 수 있다. 키오스크의 잠금(views.py 의 kiosk:{REMOTE_ADDR})이 이 값을 쓰므로, 운영에서 어떻게 동작할지는 코드를 읽고 한 추정이고 확인하지 않았다.
  • 이 문서의 Caddy 자동 HTTPS 설명은 Caddy 의 일반적인 동작을 말한 것이고, 이 저장소에서 인증서를 실제로 받아 본 결과가 아니다.
