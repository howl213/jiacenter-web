# 아동 개인정보 보호 설계 (main)

2026-11-11 사용자와 정한 방향. **구현 전의 설계**이고, 코드에 들어간 것은 아직 없다.
구현하면서 달라진 점은 이 문서가 아니라 코드와 커밋을 기준으로 본다.

## 우선순위 (사용자 결정)

센터 사용 허락, 키오스크, 경기도 알림톡 API, 배포 방식은 **확정되어야 현실이 되는 것**이라 후순위다. 그 전에는 센터가 어떻게 되든 성립하는 **코드 쪽만** 만든다.

| | 지금 한다 | 후순위 (센터·배포 확정 뒤) |
|---|---|---|
| 내용 | 칸 암호화, 조회용 HMAC, 키를 환경변수로 받기, 평문 복사본 정리, 동의·만료 칸, 익명화 기능과 실행 기록, 시험 | 저장 위치 확정, 키 보관 위치·보유자·분실 시 복구, 동의 갱신 운영, 알림톡 실제 발송, 종이 출력, 센터 PC 암호화·백업 안내 |

## 정해진 것 (사용자 결정)

| 항목 | 결정 |
|---|---|
| 보관 기한 | **1년은 개인정보 동의 유효기간**이다. 만료 전에 동의를 갱신하지 않으면 식별 정보(이름·연락처)를 지운다 |
| 출결 기록 | 법정 보관 기한이 확정될 때까지 **지우지 않는다**(보조금 증거서류 5년에 해당할 수 있다 — `docs/확인사항.md` C). 식별 정보만 익명화하고 날짜·시각·사유는 남긴다 |
| 익명화 | 동의 만료·퇴소 때 쓴다. 익명화된 기록이 증거서류로 인정되는지는 확인하지 못했다(성남시 문의에 함께 묻는다) |
| 저장 위치 | 센터 PC(센터장 로컬) 또는 종이 출력이 유력하나 **후순위**. 센터 사용 허락과 배포 확정 뒤 정한다 |
| 값 전환 | 모의 값 → 실제 값은 코드 수정 없이 한다. 키와 위치는 환경변수로 뺀다 |

## 무엇을 어떻게 지키나

값을 **다시 읽어야 하는지**로 방법이 갈린다.

| 값 | 다시 읽나 | 방법 |
|---|---|---|
| 이름, 보호자 연락처 | 예 (직원 화면, 알림톡) | **칸 단위 암호화**(인증된 암호화, 예: AES-GCM). 해시는 되돌릴 수 없어 쓸 수 없다 |
| 인식번호(`Child.code`), 출석번호 | 비교만 | 조회용 **HMAC**(비밀키 포함 해시) 칸을 따로 둔다. 키 없는 일반 해시는 자릿수가 작아 역산된다 |
| 비밀번호 | 비교만 | 이미 Django 해시 |
| 디스크 | — | 센터 PC의 디스크 암호화(FileVault/BitLocker)가 첫 방어. 칸 암호화는 그 위에 더한다 |

### 키

- 암호화 키와 HMAC 키는 **서로 다른 키**로 둔다. 둘 다 저장소·DB·로그에 두지 않고 환경변수(또는 PC 안의 별도 파일)로 받는다.
- 키가 없으면 서버가 뜨지 않게 한다(`DJANGO_SECRET_KEY` 와 같은 방식).
- 키를 잃으면 이름·연락처를 복구할 수 없다. **키 백업은 데이터 백업과 다른 곳**에 둔다.
- 키 교체를 할 수 있게 암호문에 키 번호를 붙인다.
- 보관 위치·보유자·분실 시 복구 절차는 후순위다. 센터 사용 허락과 배포 방식이 확정된 뒤 정한다(`확인사항.md` E "키 관리 설계").

### 코드에서 평문이 복사된 곳 (암호화에 함께 넣는다)

코드를 읽어 확인한 곳이다.

| 위치 | 평문으로 들어 있는 것 |
|---|---|
| `Child.name`, `Child.guardian_tel` | 원본 |
| `NotifyLog.tel`, `NotifyLog.body` | 연락처, 본문 속 아동 이름 |
| `AttendanceLog.label` | `번호. 이름` (`str(child)`) |
| `Attendance.note` | 직원이 쓰는 자유 입력. 병원 등 민감한 내용이 들어갈 수 있다 |
| CSV 내보내기 | 파일에 이름이 들어간다. 파일 보관은 직원 몫이라 암호화 대상이 아니다 |

### 암호화하면 깨지는 것 (구현 때 함께 고친다)

- `ChildAdmin.search_fields = ['name', 'code']` — 암호화된 칸은 DB에서 검색할 수 없다. 이름 검색은 포기하거나 조회용 칸을 쓴다.
- 키오스크의 인식번호 조회(`_find_child`) — HMAC 칸으로 찾는다.
- `Child.code` 유니크 제약 — HMAC 칸에 건다.
- 명단 CSV 가져오기(`center/importer.py`)의 인식번호 중복 검사.

## 동의와 익명화

- 동의 일자와 만료 일자를 아동별로 기록한다(칸 추가).
- 만료가 다가오면 직원 화면에 알린다(예: 만료 30일 전부터).
- 익명화: 이름 → `퇴소 #번호`, 연락처 → 빈 값, 인식번호 → 비움. `NotifyLog`·`AttendanceLog.label` 도 같이 처리한다. 출결 행은 그대로.
- 익명화를 실행하면 **무엇을 언제 했는지 기록**을 남긴다(표준 개인정보 보호지침 제10조 3항, 확인한 사실은 `확인사항.md` C).

## 구현 순서

1. 암호화 칸과 HMAC 칸 추가, 키 환경변수 도입, 마이그레이션(기존 모의 값은 변환)
2. 복사본(`NotifyLog`, `AttendanceLog.label`)과 admin·키오스크·가져오기 조회 수정
3. 동의 일자·만료 칸과 안내
4. 익명화 기능과 실행 기록
5. 시험: 키 없을 때 기동 실패, DB 파일에 평문이 없음, 조회·가져오기·내보내기 동작, 익명화 후 출결 보존

## vuln 쪽 (별도 작업)

팀 실습용 A04(암호화 실패) 항목은 이 설계와 짝이 되게 따로 만든다 — 브라우저 JS에 키 하드코딩, base64를 암호화로 착각, 키 없는 약한 해시 등. 삽입 목록(`docs/vuln-manifest.md`)에 먼저 적고 합의한다. 이 문서의 내용은 vuln 으로 가져가지 않는다.
