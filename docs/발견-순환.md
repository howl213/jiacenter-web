# 팀 발견 → main 수정

목적: 팀이 찾아내는 **의도하지 않은** 취약점을 안전한 껍데기(`main`)의 결함으로 되돌려 고친다.
`vuln` 은 `main` 에서 방어를 벗겨 만들었으므로, 심지 않은 곳에서 나온 발견은 `main` 에도 있을 가능성이 높다.
(이 가정은 아직 검증된 적이 없다. 발견이 쌓이면 "main 에서도 재현됐는가" 비율로 확인한다.)

## 절차

1. **접수** — 팀 저장소의 이슈(공통 규칙: 항목·재현·영향·권고)를 `.github/ISSUE_TEMPLATE/finding.yml` 양식으로 이 저장소에 옮긴다
2. **분류** — 삽입 목록에 있나?
   - 있다 → **의도.** 목록의 상태를 "발견됨"으로 적는다. 끝
   - 없다 → **비의도.** 3번으로
3. **main 에서 재현** — 같은 절차를 `main` 코드로 해 본다
   - 된다 → **main 결함.** 4번으로
   - 안 된다 → vuln 에서만 생긴 결함(예: 심은 코드의 부작용). 고칠지 목록에 추가할지 정한다
4. **main 수정** — 순서를 지킨다
   1. 재현을 **실패하는 시험**으로 먼저 쓴다 (고치기 전 코드에서 실패함을 확인)
   2. `main` 계열 브랜치에서 고치고 PR → 병합
   3. `vuln` 에는 합치지 않는다. 수정은 `main` 에만 들어간다 (두 갈래가 섞이지 않았는지는 `scripts/check_track.py`)
5. **종결** — 팀 규칙: 최초 발견자가 `secure` 재검증 후 종결. 이쪽은 결과를 커밋·PR 본문에 적는다

## 보고할 때

숫자 두 개를 함께 적는다: "의도한 N개 중 발견 K개", "비의도 발견 M건 중 main 결함 L건".
**"찾지 못했다 = 없다"가 아니다.** 팀이 못 찾은 것은 확인하지 못한 것으로 남긴다.

## 미확인

- 이 순환이 실제로 돌아 본 적이 없다 (팀 진단은 11/10 이후)
- 팀 저장소 이슈와 이쪽 이슈를 자동으로 잇는 것은 없다 (손으로 옮긴다)
