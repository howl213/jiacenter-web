### 이상한 입력 점검 — 2026-11-06 (OWASP A10, 예외 처리)

임시 테스트 DB 에 `DEBUG=False` 로 요청 25종을 보냈다. 점검 스크립트는 저장소에 두지 않았다.
**500 오류가 난 것은 5건이다.** 3건은 로그인 없이 열리는 키오스크, 2건은 직원 로그인이 필요한 현황판이다.

| 위치 | 입력 | 결과 |
|---|---|---|
| `/attendance/` (로그인 없음) | 번호 `²` (유니코드 윗첨자 숫자) | **500** `int('²')` ValueError — `isdigit()` 는 통과하지만 `int()` 가 실패 |
| `/attendance/` (로그인 없음) | 5000자리 숫자 | **500** 정수 변환 4300자리 제한 |
| `/attendance/` (로그인 없음) | `child=abc` | **500** pk 에 글자 |
| `/attendance/board/` (직원) | `child` 항목 없음 | **500** `MultiValueDictKeyError` |
| `/attendance/board/` (직원) | `child=abc` | **500** pk 에 글자 |
| `/attendance/board/` (직원) | 사유(status)에 `아무거나` | 에러는 없으나 **그대로 저장됨.** 5가지 선택지 검사 없음 |

문제 없던 것: 빈 값, 글자, 20자리 수, 날짜·시간·월 형식 오류, 공지 page=abc/-1, 없는 공지 id → 200/302/404.
확인하지 못한 것: 500 응답 본문에 내부 정보가 없는지는 화면으로 보지 않았다 (`DEBUG=False` 라 일반 오류 화면일 것으로 보이나 미확인). fail-open 은 로그인·권한 경로에서 발견하지 못했으나 전수 점검은 아니다.
**500 5건은 같은 날 고쳤다** (`center/views.py` 의 `_pk()`). 같은 25종을 다시 보내 500 이 0건임을 확인했고, 재발 방지 테스트 2개를 추가했다 (고치기 전 코드에서는 이 테스트가 실패함을 확인, 전체 13개 통과). 사유(status) 임의값 저장도 고쳤다: 선택지 밖의 값이면 기록을 만들지 않고 돌려보낸다 (테스트 추가, 검사를 뺀 코드에서는 실패함을 확인, 전체 14개 통과).

### 시도 제한 — 2026-11-06

로그인(`/admin/login/`)은 **같은 IP 에서 같은 아이디로** 5분에 5번 틀리면 5분간 그 쌍을 잠그고(맞는 비밀번호도 429), 아이디를 바꿔가며 찍는 경우는 IP 하나당 15분에 30번에서 막는다. 성공하면 그 아이디의 실패 기록을 지운다.
키오스크는 IP 당 1분에 "없는 번호" 10번이면 1분간 잠근다.
처음에는 IP 만 봤다가 "공유기 뒤에서 한 명의 오타가 관리자까지 막는다"는 지적으로 위처럼 바꿨다.
테스트 6개 추가 (전체 20개 통과). 규칙마다 그 규칙만 뺀 코드에서 해당 테스트가 실패함을 확인했다 (아이디 구분 / 성공 시 초기화 / IP 전체 한도).

한계 (코드에 `shortcut:` 주석으로도 남김):
- 같은 공유기에서 누가 `admin` 을 5번 틀리면, 관리자는 그 5분 동안 **그 공유기에서** 로그인하지 못한다 (다른 네트워크에서는 가능)
- 키오스크는 IP 기준이라 잠기면 그 1분 동안 모든 아이가 못 누른다. 센터 규모에 맞는 한도는 실제 사용 전 미확인
- 메모리 캐시라 서버를 재시작하면 카운트가 사라지고, 워커가 여러 개면 한도가 그 수만큼 늘어난다
- 프록시 뒤에서는 `REMOTE_ADDR` 가 프록시 주소가 된다 — 배포 시 실제 클라이언트 IP 처리 필요
- 브라우저에서 잠금 화면(429 문구)이 실제로 어떻게 보이는지는 확인하지 않았다

### 보호자 계정 — 2026-11-06

보호자는 `/login/` 으로 로그인하고 `/my/` 에서 자기 아이의 최근 30일 출결(날짜·입퇴실·사유)만 본다. 계정은 직원이 admin 에서 만들고, 아동 항목의 "보호자 계정" 칸에 연결한다. 보호자 스스로 가입하는 기능은 없다.
테스트 6개 추가 (전체 26개 통과). 소유권 필터를 뺀 코드에서는 "남의 아이가 안 보인다" 테스트가 실패함을 확인했다.
`/login/` 도 직원 로그인과 같은 시도 제한을 쓴다. 보호자는 `/attendance/board/`·`export/` 에 들어가지 못한다 (직원 로그인 화면으로 보내짐).

확인하지 못한 것:
- 사용자가 브라우저에서 `parent01` 로 로그인해 `/my/` 에 연결한 아이만 나오는 것을 확인했다 (2026-11-06). 표 간격은 좁아 보이며 디자인은 나중에 전면 교체 예정
- 보호자가 둘 이상일 때 서로의 아이가 안 보이는 것은 테스트(자동)로만 확인했고 브라우저로는 보지 않았다
- 보호자 로그인 상태에서 현황판(`/attendance/board/`) 접근 차단을 사용자가 브라우저로 확인했다 (2026-11-06, 문제 없음)
- 보호자 계정 비밀번호 정책(길이 등)은 Django 기본값 그대로다
- 한 보호자에게 여러 아이를 연결한 경우는 코드상 되지만 테스트하지 않았다
- 비밀번호 분실 시 재설정은 직원이 admin 에서 바꿔 주는 방식뿐이다

### 보호자 계정 한 개 제한 — 결정 대기 (2026-11-06)

지금은 아동 한 명에 보호자 계정을 **하나만** 연결할 수 있다 (`Child.guardian` 이 외래키 한 개). 그래서 아버지·어머니가 각자 로그인할 수 없고, **계정 하나를 같이 써야 한다.** 이렇게 가기로 했다 (A안).

- 문제: 아이디·비밀번호를 여럿이 공유하게 된다. 누가 봤는지 구분이 안 되고, 한 명이 비밀번호를 바꾸면 다른 사람이 못 들어간다
- 나중에 할 것: 아동 한 명에 보호자 계정을 여러 개 연결 (다대다). 형제자매를 한 계정으로 보는 것도 같이 된다. 공유 계정 문제를 풀려는 목적이다
- 바꿀 때 영향: `Child.guardian` 모델과 마이그레이션, `/my/` 의 소유권 필터 한 줄(`views.py` `my()`), 관련 테스트, admin 화면
- 시점: 실제 데이터가 쌓이기 전이 쉽다. 지금은 모의 값이라 부담이 적다

### 센터 정보 편집 — 2026-11-06

센터 이름·전화·주소·운영시간을 DB(`CenterInfo`, 한 행)로 옮겼다. admin 의 "센터 정보"에서 고치면 모든 화면에 반영된다. 마이그레이션이 `settings.CENTER` 의 더미 값으로 첫 행을 만들고, 행이 없으면 `settings.CENTER` 를 그대로 쓴다. admin 에서는 두 번째 행을 만들거나 지울 수 없다.
테스트 4개 추가 (전체 30개 통과).

확인하지 못한 것:
- 사용자가 브라우저에서 admin 의 센터 이름을 바꿔 소개 화면에 반영되는 것과, 목록에 "센터 정보 추가" 버튼이 없는 것을 확인했다 (2026-11-06)
- 슈퍼유저가 아닌 직원 계정은 "센터 정보" 수정 권한을 따로 받아야 보인다. 권한 부여 방식(그룹 등)은 정하지 않았다
- 요청마다 쿼리 1번이 늘었다 (`shortcut:` 주석). 트래픽이 늘면 캐시가 필요하다

### 출결 변경 이력 — 2026-11-06

출결이 바뀔 때마다 `AttendanceLog` 에 "대상·경로·바꾼 직원·시각·이전·이후"를 한 줄 남긴다. 경로는 키오스크, 현황판(입실·퇴실 토글과 수기 수정), admin 세 가지이고, 값이 실제로 달라졌을 때만 남긴다. admin 의 "출결 변경 이력"에서 읽기만 되고 추가·수정·삭제는 막았다. 출결 행을 지워도 이력은 남는다.
테스트 5개 추가 (전체 35개 통과). 현황판 쪽 기록을 뺀 코드와 admin 쪽 기록을 뺀 코드에서 각각 테스트가 실패함을 확인했다.

한계:
- 코드를 거치지 않은 변경(DB 파일 직접 수정, 셸의 `update()`·`bulk_update()`)은 이력이 남지 않는다
- 키오스크 변경은 "바꾼 직원"이 비어 있다 (로그인이 없는 화면이라 구분할 수 없다)
- 이력 화면은 admin 읽기 전용뿐이다. 현황판에서 아이별 이력을 보는 화면은 만들지 않았다 (디자인 교체 때)
- 변경 이력 보관 기간·용량 정책은 정하지 않았다. 지울 수 없게 막아 둔 상태라 계속 쌓인다
- 브라우저에서 admin 의 "출결 변경 이력" 화면을 직접 보지 않았다 (자동 테스트로만)

### 공지 검색 — 2026-11-06 (로드맵 5단계 첫 부분)

공지 목록(`/notices/?q=`)에서 제목·내용을 검색한다. 로그인 없이 쓰는 공개 화면이다. ORM 필터만 쓰고 검색어는 100자로 자른다.
테스트 6개 추가 (전체 41개 통과). 시험하다가 **NUL 문자(`\x00`)를 검색어로 보내면 SQLite 의 LIKE 가 패턴을 거기서 끊어 모든 공지가 일치하는 것**을 발견해 NUL 을 미리 빼도록 고쳤다 (빼는 코드를 지우면 테스트가 실패함을 확인). SQL 인젝션은 아니고 결과가 부정확해지는 문제였다.
공지 본문은 원래 `linebreaks` 필터(HTML 을 이스케이프한 뒤 줄바꿈만 변환)로 출력한다. 굵게·표 같은 **서식은 아직 없고**, 서식을 넣으려면 `|safe` 가 아니라 Markdown 등 안전한 변환이 필요하다 (미결정).
아동 검색은 만들지 않았다 — admin 의 아동 목록에 이름·인식번호 검색이 이미 있다.
브라우저 확인 (사용자, 2026-11-06): 검색창에 `<b>굵게</b>` 를 넣으면 굵게 변하지 않고 글자 그대로 보이며 "해당하는 공지가 없습니다"가 뜬다 (이스케이프 확인). 로컬 DB 에 검증용 공지 11건을 임시로 만들어 검색 + 페이지 넘김을 확인한 뒤 11건만 지웠다 (공지 수 3 → 3): 1페이지 10건, 2페이지 1건, 이전·다음 링크에 검색어 유지, 범위 밖 페이지는 마지막 페이지로 처리.
확인하지 못한 것: 공지가 수천 건일 때의 속도(`LIKE '%...%'` 라 인덱스를 못 쓴다), 나머지 브라우저 화면(제목·내용 검색 결과, 빈 검색어).

우리 시스템에 미치는 영향:
- 출결 기록이 보조금 증거서류에 해당하면 5년 보관 의무가 걸리고, 기한 전에 지우는 것이 위반이 될 수 있다. 그래서 `SECURITY_REVIEW.md` M-10(퇴소 아동 익명화·파기 기능)은 **기한 확정 전에는 만들지 않는다**
- 파기를 구현할 때는 표준지침 제10조 3항에 따라 **무엇을 언제 파기했는지 기록**도 남겨야 한다
- 현재 시스템은 출결 변경 이력을 지울 수 없게 막아 두었다 (로드맵 4단계)

확정하려면: 관할 지자체·상위기관과 「지역아동센터 지원 사업안내」에 확인한다 (C 표의 정산 양식·개인정보 동의 문의와 함께 묻는다).

### 성남시 기준 확인 — 2026-11-06

이 시스템은 성남시 기준으로 갈 예정이다. law.go.kr 의 자치법규에서 「성남시 지역아동센터 운영 및 지원에 관한 조례」(조례 제3991호, 시행 2023.12.11 판, 연혁 11건 중 가장 최근)를 읽었다.

- 제1조~제20조 본문을 읽었다. 페이지 전체에서 "보존·보관·서류·장부·기록·파기·개인정보"를 검색했고 **일치가 0건**이었다. 즉 **서류 보존기간이나 파기 기준은 이 조례에 없다**
- 관련 있어 보이는 조항: 제9조(시장의 지도·점검 — 운영, 종사자, **재정관리** 상태), 제14조 2항(시립센터 수탁자는 결산안을 회계연도 종료 후 3월 말까지 제출). 제14조는 **시립센터**에 대한 것이라 이 센터가 시립센터인지에 따라 적용 여부가 다르다 (미확인)
- 읽지 못한 것: 제20조 이후 조문과 부칙, 성남시 규칙(시행규칙), 시의 운영 지침·지침 공문. 웹 검색으로도 성남시의 보존기간 기준은 나오지 않았다
- 결론: 성남시 기준의 보존기간은 **확인하지 못했다.** 조례가 아니라 성남시 아동 담당 부서의 운영 지침이나 「지역아동센터 지원 사업안내」에 있을 가능성이 높으나 이는 추측이다. 담당 부서에 직접 묻는다

### 보관 방침 (제안, 기한 확정 전까지 임시) — 2026-11-06

| 항목 | 방침 |
|---|---|
| 기준 | 용량이 아니라 **기간**으로 정한다. 용량 기준으로 자동 삭제하면 아직 보관 중인 기록이 지워질 수 있다 |
| 보관 기간 | 확인된 것은 보조금 증거서류 5년(시행령 제10조의2)뿐이다. 출결이 여기에 해당하는지와 5년을 **어디서부터 세는지**는 미확인이므로, 확정 전까지는 **아무것도 지우지 않는다** |

| 용량 | 자동 삭제 기준으로 쓰지 않는다. 일정 크기를 넘으면 직원에게 **알리기만** 한다 |

| 정할 것 | 5년의 기산점, 성남시의 별도 기준, 경고를 띄울 크기 — 모두 실제 서비스 전환 전까지 |

이 방침은 확인된 법령을 바탕으로 한 제안이며, 성남시 기준과 다를 수 있다.

### 오래된 기록을 CSV 파일로 옮기는 방안 — 결정 대기 (2026-11-06)

사용자 제안: DB 가 무한정 커지는 것을 막기 위해 주기적으로 CSV 로 내보내 파일로 관리한다.

측정한 것 (임시 DB, 이 기기, 가정한 조건):
- 아동 50명 × 평일 5년(1,305일) = 출결 65,250행 + 변경 이력 130,500행을 넣고 화면을 불러 봤다
- 현황판 25~31ms, 3년 전 날짜 현황판 25ms, 월별 CSV 내보내기 45ms, `/my/` 4ms, 키오스크 15ms (5회 평균). 가정이 실제 센터와 다르거나 다른 기기에서는 달라질 수 있다

따라서 **지금 규모에서는 DB 크기가 문제가 된다는 근거가 없다.** 반대로 CSV 로 옮기면 생기는 문제:
- 아동 이름이 든 파일이 DB 밖에 새로 생긴다. DB 와 같은 수준의 암호화·접근 통제와 키 관리가 필요하다 (E 표의 키 관리 설계)
- 파기 의무가 CSV 사본에도 똑같이 걸린다 (표준지침 제10조)
- DB 에서 지운 뒤 5년 보관 의무가 걸리면 CSV 가 증빙이 된다. 변경 이력의 무결성(고쳐지지 않았다는 것)을 파일로 보여주기는 DB 보다 어렵다

월별 CSV 내보내기는 이미 있다 (정산용). 그래서 당분간은 **아무것도 만들지 않는다.** 다시 볼 조건: ① 보관 기한이 확정되었을 때 ② 실제 데이터가 쌓여 느려지는 것이 측정되었을 때. 그때 하게 되면 "내보내기 + 파일 해시 기록 + 암호화 보관 + 보관 기한 지난 것만 DB 에서 삭제" 순서로 설계한다.

## 결정 기록 — 2026-11-06

사용자가 정한 것, 확인한 것, 확인하지 못한 것을 나눠 적는다.

### 사용자가 정한 것

| 항목 | 결정 |
|---|---|
| 데이터 | 완성될 때까지 **모의 값만** 쓴다. 완성 후 허락을 받고 실제 서비스로 전환 |

| 껍데기 방식 | 모의 값이 든 껍데기를 먼저 완성하고 값만 바꿔 전환한다. 값을 바꾸려고 코드를 고쳐야 하면 껍데기가 덜 된 것 |
| 아동 정보 암호화 | main 에서 해결한다 (키 관리 설계가 먼저 — 위 E 표). vuln 에서는 평문 그대로 둔다 |
| 게시판·댓글·회원가입 | **vuln 전용**, 점검용. 인증은 임시 권한(간편 로그인 또는 전화번호 인증) 개념이며 모의 값으로 한다. 구현은 6단계 |
| 도메인 | 1년치 구입 (사용자 말, 미확인). 서버는 운영 배포 테스트 때 설정 |
| 브랜치·문서 | 팀 레포와 별개로 이 레포 규칙대로 (`vuln/practice` 예정) |

| OWASP 번호 | **2025판으로 바꾼다** (사용자 결정) |

### 확인한 것

팀 레포 `SJH910/Web-Hacking` (비공개) 의 `README.md`, `PLAN.md`, `plan/tasks.md`, `plan/tasks-summary.md` 를 읽었다.

- 일정: 웹앱 구현 11/9~11/12, 마감 11/23 (목표 11/20)
- 팀 `README.md` 는 기준을 **OWASP Top 10:2025** 로 적었다. 반면 `PLAN.md` 의 "정해야 할 것" 에는 "2025 또는 2021" 이 체크되지 않은 채 남아 있다
- 공식 페이지(owasp.org/Top10/2025)에서 받은 2025판 항목 이름 10개가 팀 `PLAN.md` 와 같았다 (2026-11-06)
- 2025판에서 SSRF 는 A01 에 합쳐졌고 A10 은 새 항목(Mishandling of Exceptional Conditions)이다. `SECURITY_REVIEW.md` 는 A10 을 점검하지 않았다

### 확인하지 못한 것

- 웹앱 구현을 11/12 까지 끝낼 수 있는지 — 사용자 판단이며 작업량은 따져보지 않았다
- 팀 일정에서 이 레포의 위치 — 사용자 설명으로는 이 레포가 웹 환경 전체를 담당하고 팀원은 진단만 한다

### 작업 순서

1. 로그인 시도 제한 + 키오스크 번호 시도 제한
2. 보호자 계정 + `/my/` (본인 아이만 조회)
3. 센터 정보 편집 화면 (`settings.CENTER` → DB)
4. 출결 변경 이력 (틀만, 범위는 시작할 때 정한다)
5. 검색·공지 서식 → 업로드·CSV 가져오기 → 알림톡·외부 임베드
6. 실습 브랜치 구성 (게시판·댓글·회원가입은 여기서 vuln 에만)
7. 운영 배포 테스트

## 상시 주의 사항

작업할 때마다 지켜야 하는 것. 체크박스가 아니라 **규칙**이다.

1. **실습본을 인터넷에 올리지 않는다.** 취약한 서버는 제3자 공격의 발판이 된다.
2. **`db.sqlite3` 를 커밋하지 않는다.** 아동 실명·보호자 연락처가 평문으로 들어 있다.
3. **`logs/error.log` 를 DB 와 같은 수준으로 다룬다.** 에러 추적에 요청 내용이 섞인다.
4. **`SECURITY_REVIEW.md` 는 답안지다.** 실습본 브랜치에 포함하지 않는다.
5. **추정한 출결 시각을 자동으로 채우지 않는다.** 보조금 정산 근거다.
6. **테스트 통과를 "안전하다"로 바꿔 말하지 않는다.** 무엇을 확인했고 무엇을 안 했는지 구분해 적는다.

## Google Drive 동기화 — 2026-11-05 발견

### 무엇을 보았나

프로젝트 폴더에서:

```
$ git status --short
?? .tmp.driveupload/          ← Google Drive 업로드 임시 폴더

$ ls -d ~/Library/CloudStorage/*
~/Library/CloudStorage/GoogleDrive-(계정 주소)
```

프로젝트 폴더 **안에** Drive 업로드 임시 폴더가 생겼다는 것은, Drive 가 이 폴더의 파일을
올리고 있다는 뜻이다.

### 왜 문제인가

`db.sqlite3`(180KB)에 아동 실명·인식번호·보호자 연락처가 **평문**으로 들어 있다.
`.gitignore` 로 깃 커밋은 막았지만, **Drive 동기화는 그것과 무관하게 파일을 올린다.**

| 경로 | 차단 상태 |
|---|---|
| Git / GitHub | ✅ `.gitignore` 로 차단 |
| Google Drive | ❌ **차단되지 않음** |
| `logs/error.log` (요청 내용 포함 가능) | ❌ 동일 |

현재는 전부 모의 데이터라 **실제 유출은 없다.** 다만 실제 아동 정보를 넣는 순간
개인정보가 개인 Google 계정으로 올라간다. 개인정보 처리 위탁·국외 이전 문제가 될 수 있다.

### 확인할 것

- [ ] Google Drive 설정에서 Desktop(또는 이 폴더) 동기화가 켜져 있는지
- [ ] Drive 에 이미 올라간 `db.sqlite3` 가 있는지, 있다면 휴지통까지 삭제
- [ ] 버전 기록(Drive 는 과거 버전을 보관한다)에 남아 있는지

### 결정 (2026-11-05)

**의도된 설정이다.** 집에서도 폴더를 보려고 동기화를 켜 둔 것이며,
**실제 아동 정보를 넣기 전에 분리**하기로 했다.

현재 데이터는 전부 모의 값이므로 그대로 둔다.

### 실제 데이터 투입 전 체크리스트

- [ ] 프로젝트를 Drive 밖으로 옮기거나(예: `~/dev/jiacenter-web`), 이 폴더만 동기화 제외
      — 코드는 GitHub 에 있으므로 폴더를 옮겨도 잃을 것이 없다
- [ ] Drive 에 이미 올라간 `db.sqlite3` 삭제 (휴지통까지)
- [ ] Drive 버전 기록에 남은 사본 확인 — Drive 는 과거 버전을 보관한다
- [ ] `logs/error.log` 도 같이 정리 — 요청 내용이 섞일 수 있다

- [ ] **보관·파기 기한 확정** — 성남시 아동 담당 부서에 문의 (5년의 기산점, 성남시 별도 기준, 출결의 증거서류 해당 여부). 확정 전까지는 아무것도 지우지 않는다 (위 "보관 방침")

이 항목이 정리되기 전에는 실제 아동 정보를 입력하지 않는다.
