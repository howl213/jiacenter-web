# 지역아동센터 홈페이지 (jiacenter-web)

지역아동센터의 공개 홈페이지와 아동 출결 관리 시스템.
Django 6.1 / SQLite / 외부 프런트엔드 없음.

현재 **초안 단계**다. 센터 실제 정보는 들어 있지 않고, DB의 아동 정보는 전부 모의 값이다.

## 빠른 시작

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python manage.py migrate
.venv/bin/python manage.py createsuperuser
.venv/bin/python manage.py runserver
```

http://localhost:8000 에서 열린다. 환경변수를 아무것도 설정하지 않으면 개발 모드로 동작한다.

테스트:

```bash
.venv/bin/python manage.py test
```

## 출결 동작

### 아이 입장

현관 단말에서 **자기 타일을 누르거나**, 번호를 치고 엔터.
기록이 없으면 입실, 입실만 있으면 퇴실, 이미 퇴실했으면 변경 없음.

번호는 두 가지를 다 받는다.

| 종류 | 자릿수 | 예 |
|---|---|---|
| **인식번호** | 4~5 | 보호자 번호 뒷 4자리. 남매는 뒤에 순번 한 자리 (`2742` / `27421` / `27422`) |
| **출석번호** | 1~2 | `7` |

자릿수가 달라 서로 겹치지 않는다. 인식번호 중복 등록은 DB 가 막는다.

### 직원 입장

`/attendance/board/` 에서 날짜를 옮겨 다니며(`?date=2026-03-14`) 입·퇴실 시각,
사유(출석/결석/조퇴/병가/기타), 비고를 직접 고친다.

### 설계상 지켜야 하는 두 가지

출결은 **보조금 정산 근거**다. 그래서:

1. **추정값을 자동으로 채우지 않는다.** 퇴실 기록이 없는 날은 현황판 상단에 경고로만 띄우고,
   사람이 확인해서 입력한다.
2. **재입력이 실제 시각을 덮어쓰지 않는다.** 하루에 세 번째부터 누르면 안내만 하고 기록은 그대로다.

### 알림톡

경기도 알림톡 API **승인 전**이다. `center/notify.py` 의 `send_alimtalk()` 는 실제로 보내지 않고
`NotifyLog` 테이블에 기록만 남긴다. 승인되면 **이 함수 안에서만** 실제 호출을 추가하면 되고,
부르는 쪽은 건드리지 않는다.

지난 날짜를 보정할 때는 알림을 보내지 않는다. "지금 도착했습니다"가 뒤늦게 가면 안 되기 때문이다.

## 환경변수와 보안 설정

개발에서는 아무것도 설정하지 않아도 동작한다. 운영에서는 환경변수로 덮어쓴다.
`.env.example` 에 견본이 있다.

| 변수 | 개발 기본값 | 운영 |
|---|---|---|
| `DJANGO_DEBUG` | `1` (켬) | **`0`** — 켜 두면 에러 화면에 설정·소스·SECRET_KEY 가 노출된다 |
| `DJANGO_SECRET_KEY` | 고정 더미값 | **필수.** 없으면 기동하지 않는다 |
| `DJANGO_ALLOWED_HOSTS` | `localhost,127.0.0.1` | 실제 도메인 |

`DJANGO_DEBUG=0` 인데 `DJANGO_SECRET_KEY` 가 없으면 **서버가 뜨지 않는다.**
기본값으로 조용히 돌아가면, 설정을 깜빡한 서버가 공개된 키로 세션을 서명하게 되기 때문이다.

운영 모드에서는 SSL 리다이렉트, Secure 쿠키, HSTS 가 자동으로 켜진다. 개발에는 https 가 없어
켜면 접속이 안 되므로 `DEBUG` 로 분기했다.

배포 전 점검:

```bash
DJANGO_DEBUG=0 DJANGO_SECRET_KEY='...' .venv/bin/python manage.py check --deploy
```

### 다루는 개인정보

`db.sqlite3` 에 **아동 실명, 인식번호, 보호자 연락처**가 평문으로 들어 있다.

- `.gitignore` 로 커밋을 막아 두었다. **절대 커밋하지 않는다.**
- `logs/error.log` 에도 요청 내용이 섞일 수 있다. DB 와 같은 수준으로 관리한다.
- 운영 PC 는 디스크 암호화(FileVault / BitLocker)를 켠다.

현재 보안 상태는 `SECURITY_REVIEW.md` 참고. OWASP Top 10:2025 기준 점검 결과와 조치
체크리스트가 들어 있다.

## 개발 워크플로

### 브랜치

```
main                        항상 동작하는 상태
  ├─ feat/기능-이름
  ├─ fix/버그-이름
  ├─ security/보안-항목
  └─ docs/문서-이름
```

### PR

```bash
git switch -c feat/보호자-계정
# 작업, 커밋
git push -u origin feat/보호자-계정
gh pr create
```

**Squash merge** 로 합친다. 작업 중 커밋이 main 에 남지 않고 PR 하나 = 커밋 하나가 되어
롤백 단위가 깔끔해진다.

> main 브랜치 보호 규칙은 걸려 있지 않다. GitHub Free 플랜에서 **프라이빗 레포는 보호 규칙을
> 쓸 수 없다**(API 응답: `Upgrade to GitHub Pro or make this repository public`).
> 규칙이 막아주지 않으므로 PR 을 거치는 것은 각자 지킨다.

### CI

`.github/workflows/test.yml` 이 PR 과 main push 마다 돈다.

1. `manage.py test`
2. `DJANGO_DEBUG=0 manage.py check --deploy`

2번은 아직 미해결 경고가 있어 실패해도 머지를 막지 않는다(`continue-on-error`).
경고를 다 잡으면 그 줄을 지운다.

### PR 본문에 쓰는 것

`.github/pull_request_template.md` 에 체크리스트가 있다. 특히 **"확인하지 않은 것"** 칸을
비우지 않는다. 테스트가 통과했다는 것과 기능이 안전하다는 것은 다른 말이다.

## 두 개의 트랙 — 운영본과 실습본

이 프로젝트는 두 갈래로 간다.

| | 운영본 | 실습본 |
|---|---|---|
| 위치 | `main` | `vuln/practice` (예정) |
| 목적 | 실제 센터 서비스 | OWASP Top 10 웹해킹 실습 |
| 데이터 | 실제 (예정) | 모의 값만 |
| 배포 | 도메인 + HTTPS + 클라우드 | **로컬 전용** |

### 실습본 취급 규칙

> ### ⚠️ 실습본은 인터넷에 올리지 않는다
>
> 모의 데이터라 개인정보 유출 위험은 없지만, 취약한 서버는 **제3자를 공격하는 발판**으로
> 쓰인다 — 악성코드 호스팅, 스캔 경유지, 스팸 중계. 클라우드 약관 위반이기도 하다.
>
> 실습은 각자 `localhost` 또는 외부와 끊긴 내부망에서만 한다.

그 외:

- `SECURITY_REVIEW.md` 는 **답안지**다. 실습본에는 넣지 않는다.
- 실습본 커밋 메시지에 어떤 방어를 벗겼는지 적힌다. 실습 전에는 커밋 이력을 보여주지 않는다.

### 실습본을 만드는 방식

두 번 짜지 않는다. **운영본을 제대로 만들고, 거기서 방어만 벗겨낸다.**

```
main (제대로 구현)
  └─ vuln/practice
       ├─ A01 — 소유자 검사 제거
       ├─ A05 — 검색을 원시 SQL 로 교체
       ├─ A05 — 공지 본문을 |safe 로 출력
       └─ A01 — 외부 URL 검증 제거 (SSRF)
```

커밋 하나 = 취약점 하나 = OWASP 항목 하나. 커밋 목록이 그대로 정답표가 되고,
운영본에 취약 코드가 섞일 일이 없다.

## 로드맵

실습 가능한 OWASP 항목을 늘리는 것과, 센터에 실제로 필요한 기능을 만드는 것은 같은 방향이다.
**공격면이 없는 이유는 코드가 훌륭해서가 아니라 기능이 없어서다.**

| 단계 | 기능 | 센터에 왜 필요한가 | 열리는 OWASP |
|---|---|---|---|
| **0** ✅ | 보안 설정 분리 | — | A04 · A02 일부 |
| **1** ✅ | 로그인·키오스크 번호 시도 제한 | 무차별 대입 차단. 보호자 로그인을 열기 전에 필요 | A07 · A06 |
| **2** ✅ | 보호자 계정 + 내 아이 출결 조회 | 학부모 문의 전화 감소 | **A01**(IDOR) · A07 · A04 |
| **3** ✅ | 센터 정보 편집 화면 | 값 교체 시 코드 수정 불필요 | — |
| **4** ✅ | 출결 변경 이력 (틀만) | 정산 근거 보존 | A06 (`SECURITY_REVIEW.md` M-09) |
| **5** | 공지 검색 ✅ → 공지 서식 ✅ → 파일 업로드·CSV 가져오기 → 알림톡·외부 임베드 (이전 로드맵의 2~4단계) | 공지 증가, 일괄 등록, 이미 계획된 기능 | A05 → A08 · A03 → A01 (SSRF) |
| **6** | `vuln/practice` 브랜치 구성. 게시판·댓글·회원가입은 여기에만 넣는다 (main 에는 없음) | — | 전체 |
| **7** | 운영 배포 테스트 | 서버·도메인 연결 | — |

A05 는 공지 검색·서식(5단계)으로 공격면이 생겼고, A10(예외 처리)은 2026-11-06 이상한 입력 점검을 했다(`docs/확인사항.md`).
A09(보안 로깅)는 main 에 아직 없다. A03 · A08 과 A01 의 SSRF 는 해당 기능 자체가 없어 공격면이 없다.

OWASP 번호는 Top 10:2025 판이다 (`SECURITY_REVIEW.md` 와 같다).

단계마다 PR 하나, CI 통과, `SECURITY_REVIEW.md` 갱신.

## 앞으로 할 것

**당장 AI로 가능**

- 파일 업로드·CSV 가져오기
- 운영 배포 설정 (HTTPS, gunicorn, 정적파일 서빙, 백업)
- 보안 로깅
- 개인정보 처리방침 초안
- 퇴소 아동 익명화 (보관 기간이 정해진 뒤)

**외부 공식 확인 필요**

- 경기도 알림톡 API 승인 (실제 발송)
- CSV 칸 구성이 지자체 정산 양식과 맞는지
- 출결 기록 법정 보관 기간 (성남시)
- 보호자 개인정보 수집·이용 동의 범위

**결정 대기**

- 키 관리 설계
- HSTS preload
- 보호자 계정 여러 명 연결
- `/attendance/` 노출 방식 (IP 제한 / 내부망 분리 / 기기 인증)

**알려진 미해결 위험**

- `/attendance/` 는 인증 없이 아동 실명 전체를 보여주고 쓰기까지 된다.
  "현관 전용 단말"이라는 물리적 전제 위의 설계이며, 코드에는 그 전제를 강제하는 장치가 없다.
  **이 상태로 인터넷에 공개하면 안 된다.** 상세는 `SECURITY_REVIEW.md` 의 A01 항목.
